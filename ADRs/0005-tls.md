# 0005: Optional TLS termination via NIOSSL

- Status: Accepted
- Date: 2026-09-04

## Context

Production HTTP/1.1 servers need TLS on the socket. Callers already have PEM-encoded keys and certificates from files, environment variables, or a secret store. Exposing NIOSSL types or channel pipelines would leak the transport that ADR 0001 and ADR 0002 keep internal.

ADR 0001 named SwiftNIO as the package's only runtime dependency. NIO does not ship a TLS implementation.

## Decision

Add an optional `tls` field on `ServerConfiguration`. Its public value is PEM strings for the private key and certificate chain (leaf first):

```swift
ServerConfiguration(
    hostname: "0.0.0.0",
    port: 8443,
    tls: .init(key: privateKeyPEM, cert: certificateChainPEM)
)
```

`listen` loads those PEMs into one `NIOSSLContext` per bind and inserts `NIOSSLServerHandler` as the first child-channel handler, before the HTTP/1.1 codec. ALPN advertises `http/1.1` only. `tls: nil` keeps cleartext as the default.

NIOSSL is a second runtime dependency. Its types do not appear in the public API. Invalid PEMs, an empty credential, or a key that does not match the leaf certificate fail `listen` with `ServerError.invalidConfiguration` before the socket is bound.

Passphrase-protected keys, client certificates, custom cipher suites, SNI-based certificate selection, and file-path loading are deferred.

## Consequences

- Enabling HTTPS is a configuration change; handlers, routing, and response framing stay the same.
- BoringSSL increases compile time and binary size relative to the cleartext-only package.
- ADR 0001's "one runtime dependency" consequence no longer holds.

## Alternatives considered

- Re-exporting NIOSSL `TLSConfiguration` would expose every knob immediately but would leak transport types.
- Network.framework TLS would be Apple-only.
